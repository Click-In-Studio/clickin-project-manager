# 审批流程模版引擎设计（2026-09-03）

> 定谳文档。承接 #405（设计器 UI 草稿）、#409（范围校准）与
> `docs/approval-flow-template-backend-gaps-2026-09-02.md`（缺口分析）。
> 本文取代 #409 中「T2 挂起」的表述：产品方向已明确（自定义审批流），按本文交付。

## 0. 结论摘要

- **核心模型**：节点 = 升级链的容器。推进是节点间事件（新能力），转交/超时升级是节点内事件（复用现有阶梯逻辑）。叶子即终局，不需要 per-node 终局标志。
- **单引擎、单编译器、双源**：提交时把「已发布模版」或「内置阶梯」编译成同一种流程实例；存量在途行懒编译，零数据迁移。
- **两段式快照**：提交时定结构（规则），逐跳晚绑定定人。已通知的跳定格，未来跳仅作预测展示。
- **默认模版两步切换**：先上行为兼容的单节点阶梯默认（零行为变化），再由产品显式切换到傻瓜配置多节点默认。
- **交付**：prA 存储层 → prB 引擎 → prC #405 接线。

## 1. 背景与目标

产品方向是可自定义审批流（对标飞书/钉钉式配置），设计沿用本软件一贯的分层：
**模版系统提供易用性，配置与引擎提供自定义性**（与项目模版、角色模版同构）。

体验控制三原则（写死，防配置复杂度砸到剧组 owner 脸上）：

1. **预设优先**：绝大多数项目选预设模版，设计器是少数 owner 的高级入口。
2. **零配置兜底**：不配置模版的项目走内置默认，永不强迫配置。
3. **渐进暴露**：v1 只放顺序节点 + 或签；会签第二步；条件分支/并行子链最后。
   「实际审批链长度」靠默认模版的傻瓜配置控制（空处理人跳过），不靠砍功能。

## 2. 核心模型：节点 = 升级链容器

```
节点 = {
  内部升级链：转交（手动/超时）沿链移动；canFinalize=false 的跳（如不持有
              权限的直属上级）只能转交——这些是节点内 resolver 元数据，不进模版语法
  完成条件：  链上某人 approve → 节点完成 → 推进到下一节点
  终局：      最后一个节点完成 = 流程完成（叶子即终局）
}
推进 = 节点间事件（新增）
升级 = 节点内事件（现有 advanceToStage 逻辑几乎原样复用）
```

关键性质：**现有整条审批阶梯 = 一个单节点模版**，行为一比一还原——
「直属上级持有权限时一步批完」自然保留（节点内 approve，且是唯一节点）。
升级循环、动态深度、canFinalize 门控全部收进节点内部，模版语法保持极小
（无条件分支、无循环）。这也与飞书/钉钉的节点心智模型一致。

## 3. 单引擎、单编译器、双源

```
提交时：
  该项目有已发布模版？
    是 → 编译模版        → 流程实例（多节点，逐节点推进）
    否 → 编译内置阶梯源  → 流程实例（单节点，语义 = 今日阶梯）
状态机只有一个：读流程实例逐节点走。
```

**存量在途行懒编译**：无 `flow_snapshot` 的行在下次被操作时现场从阶梯编译。
不做一次性回填——改写 `approval_request` 现存行属于数据迁移，会触发 migration
规约全套（migrate-*.sql + 三层测试），为少量行不值得。

## 4. 快照模型（两段式）

**第一段——提交时定结构**：节点序列、每节点的处理人来源规则、超时与空处理人
策略、模版引用，随提交定格进 `flow_snapshot`。此后模版怎么改都不影响在途实例
（防「链走到一半上游变了、下游悬空」）。

推论：**每个实例自带版本 pin**。模版版本控制因此从正确性需求降级为管理审计
需求（谁改的、何时改的），挂收尾 issue，不阻塞引擎。

**第二段——逐跳定人（晚绑定）**：进入节点 / 节点内升级触发的那一刻，才把该跳
的规则解析成具体的人。理由：

1. 今日阶梯就是逐跳按最新组织关系重算，兼容默认必须保持（零行为变化红线）；
2. 成员退出/角色变动自愈：不会有申请死在快照住的离场者身上；
3. 审批找的是「权」不是「人」——剧组角色随排练阶段流动，节点存活期以天/周计；
4. 与既有定谳同哲学（链上人名按当前 user_profile 现算，2026-08-25）。

**定格规则**：一跳一旦解析并通知（`current_approver_ids` 写入）即定格，组织
变动不静默撤换已通知的人；重解析仅由显式事件触发（下一次转交/超时、成员退出
清理钩子）。已走跳永久落审计链。**未来跳仅作实时预测展示，标注为预测，不作
执行承诺**——这也是 requestId 实例接口（缺口文档 P1-6/P1-7）的展示口径。

## 5. 默认模版：两步切换

1. **兼容默认**（随 prB 上线）：单节点阶梯模版。全量项目切到新引擎当日
   **零行为变化**——出问题能分清是引擎错还是模版设计错。
2. **产品默认**（独立的显式决策，随「剧组版审批流」提案定）：傻瓜配置多节点
   模版，如「直属上级节点 optional=空则跳过 → 资源负责人 → …」。注意多节点后
   直属上级 approve 从「可能终局」变为「完成本节点推进下一节点」——这是产品
   要的行为（接受更长流程），但必须作为默认模版内容的显式切换，不随引擎静默发生。

## 6. v1 边界

**做**：approval 顺序节点；多人策略仅或签（any）；cc 节点 = 到达时通知投递
（复用通知基建，不做送达/已读审计）；processing 节点 = 「批准 ≠ 发行」两段态
（把 `approveAccessRequest` 中的发行段拆出延迟执行）；空处理人策略
{跳过 | 兜底 owner}；节点超时（沿节点内链升级，链尽头走空处理人策略）。

**不做（挂收尾 issue）**：会签/依次（all/sequential）的独立 response 记录
（但快照结构为其预留 `responses[]`）；条件分支；OR/并行子链；模版版本链与
审计；超时策略细分（提醒/委托/自动拒绝）；并发编辑 ETag；已发布版本删除约束。

## 7. 数据与接口草案

- 新表 `approval_flow_template`（`db/add-*.sql`，TEXT short id PK 带随机尾，
  新表 id 规约）：production_id FK、name、description、resource_scope、
  status(draft/published)、nodes JSONB、updated_by、updated_at。
- `approval_request` 增列（`db/add-*.sql` 纯增列）：`flow_snapshot` JSONB
  （可空 = 存量懒编译）、模版引用。快照内每节点预留 `responses[]`
  （人、决定、时间、意见）供会签扩展，v1 只写单条。
- REST：模版 CRUD + publish（owner 门）；`GET …/access-requests/:requestId/flow`
  实例接口（快照 + 已走跳审计 + 当前跳 + 未来跳预测 + 当前用户可执行动作）。
- 服务端运行时枚举白名单校验 type / assigneeSource / decisionMode。
