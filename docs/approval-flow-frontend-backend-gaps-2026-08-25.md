## 本次前端已接入的后端能力

- `approval_request.escalation_chain`：展示已经经过的审批节点、节点层级、候选审批人、通知时间、动作、操作人和操作时间。
- `current_stage` / `current_approver_ids`：标识当前审批节点与相关人。
- `approve` / `reject` / `escalate` / `cancel`：分别对应批准、拒绝、沿既定阶梯向上转交、申请人撤回。
- 动态审批阶梯：直属上级 → 资源持有人 → 资源负责人/部门 POC → 上级部门 POC → 制作人 → Owner；无人的节点由后端跳过。
- 前端通过项目通讯录把审批链中的用户 ID 映射为姓名和项目角色。通讯录不可用时，流程仍可展示，但人员降级为“项目成员”。

## 与目标设计存在的冲突或缺漏

| 目标能力 | 当前后端现状 | 本次前端处理 | 后端建议 |
| --- | --- | --- | --- |
| 提交前展示完整审批链和相关人 | 后端按实时组织关系动态计算，只持久化已经进入过的节点；没有预览接口 | 表单只展示路由规则，详情页展示真实历史和当前节点，并提示后续动态计算 | 增加只读 `approval-preview` 接口，明确返回“快照”还是“预测” |
| 人员姓名、头像、角色快照 | 审批数据只返回用户 ID | 临时联查 `/contacts` | 在审批 DTO 中返回人员展示信息，或在链条中保存操作时快照，避免离职/改名后历史失真 |
| 抄送节点 | 无节点类型、抄送人、通知/已读/归档字段 | 不展示虚构抄送节点 | 增加 `nodeType=cc`、recipient IDs、notified/read 时间及历史记录 |
| 处理节点 | 权限申请批准后直接发放权限，没有独立处理人、处理状态或完成动作 | 当前资源权限申请只展示审批节点 | 增加 `nodeType=processing`、处理人、待处理/完成/失败状态及完成接口；报销、IT 权限等应由领域处理器执行 |
| 审批评论与拒绝原因 | 动作接口不接收评论，链条无评论字段 | 不提供无效输入框 | 增加动作备注或独立评论表/API，保留作者、时间、可见范围和附件 |
| 转交给指定人员 | `escalate` 只能沿后端计算的固定阶梯进入下一节点 | 按真实语义显示“向上转交” | 如需飞书式任意转交，增加 target user、资格校验及原/新处理人审计记录 |
| 退回 | 阶梯被设计为单调向前，不支持回退 | 不展示“退回”按钮 | 明确退回到发起人还是上一节点，并增加补充后重提的状态机 |
| 会签/或签 | 同一节点有多人时，任一有权人操作即可完成节点 | 人员并列展示，不宣称需要全员批准 | 增加节点策略 `any/all/sequential` 及每个人的独立决定记录 |
| 完整结束语义 | 权限申请只有批准、拒绝、撤回；“处理完成”不是独立终态 | 按现有终态展示 | 将审批决定与业务处理结果拆分，避免“批准”等同于“已办结” |
| 存量历史链 | 部分已结束的演示/存量记录没有 `escalation_chain`，只能取得 `resolvedBy/resolvedAt`；演示数据还存在解决时间早于创建时间的情况 | 降级显示“历史审批记录”，不虚构具体审批角色 | 回填历史链，并增加 `resolved_at >= created_at` 的写入校验或数据修复 |
| 跨业务统一收件箱 | 权限审批与财务审批使用相似路由但不同数据表，本页只读取权限申请 | 保持“资源申请”页面边界 | 定义统一审批 DTO/聚合 API，再承载报销、IT、IP、P4 等流程 |

## 产品语义说明

- **审批**：当前系统已具备，负责判断合规性与可行性，可批准、拒绝或沿既定链路向上转交。
- **抄送**：当前系统尚未建模，应只承担知会、追溯与存档，不应拥有审批决定权。
- **处理**：当前系统尚未建模，应表示审批通过后的实际执行事项；处理人完成业务动作后，流程才能真正办结。

在上述后端能力补齐前，前端不得用纯本地状态伪造评论、抄送、处理、任意转交或退回，以免页面显示成功但审计链和实际业务状态没有变化。
