> 关联 [#526](https://github.com/Click-In-Studio/clickin-project-manager/issues/526)。
> 状态：用户已授权开始实现，当前实现决策见 §10；§1–§9 保留调研与备选推导。
> 已修改本地代码；未修改生产数据库或现有正文。
> 下文区分已验证事实、建议契约和待决项。示例素材 id 均为虚构。
> 二次调研修订：撤回“单元格内部只用 HTML”的建议。单元格复用现有 Markdown

## 1. 问题与证据

### 1.1 线上案例

经用户授权，只读查看指定 wiki 正文及该文档的引用边、embed 挂载数量。
不在仓库保留原文、真实素材 id、图片、人员信息或生产库导出。

| 表格 | 行列 | 图片数 | 空段落数 | 宽度 |
| --- | --- | --- | --- | --- |
| A | 1 × 4 | 4 | 0 | 820px |
| B | 1 × 3 | 3 | 3 | 612px |
| C | 1 × 2 | 2 | 2 | 406px |
| D | 1 × 4 | 4 | 7 | min-width 646px |

四张表均无表头、无合并格，用于并排展示参考图。已存内容同时含图片展示
`src` 和素材身份 `data-cm-src`，是经过本站处理的存储样本，不能当作飞书
原始剪贴板证据。用相关编辑器扩展重建后，四张表分别原样往返，保真锁均未报警。

对整篇正文运行现有 `extractMentionEdges`、`extractEmbedAssetIds`，结果均为空；
线上对应的正文素材引用边与 embed 挂载数量也均为 0。提取器只认 Markdown
链接、图片形态，未读取 HTML 图片身份。此结果不证明图片对所有观看者均不可见，
其他权限路径未逐人核查。

### 1.2 代码中的边界

- `lib/editor/feishu-paste.ts`：飞书粘贴归一化，没有完整表格契约。
- `lib/editor/tiptap-table-markdown.ts`：首行全表头、无跨格、每格单块等条件
  决定是否输出 GFM；否则委托上游输出 HTML。这个判断尚不足以证明无损。
- `lib/wiki/tiptap-image.ts`：图片的 Markdown serializer 存身份 URI；
  HTML 回退走节点的 `renderHTML`，可把展示地址也写入正文。
- `components/wiki/WikiMarkdown.tsx`：未解释 HTML 表格；引用预收集依赖
  Markdown 链接形态。仅替换最终 table 组件不能补齐上游引用收集。
- `lib/wiki/links.ts`：正文派生引用及素材 embed 挂载的写入方。
- `lib/wiki/fidelity.ts`：内容签名多重集检查不验证单元格坐标和结构。
- `lib/editor/line-merge.ts`：按文本行三路合并，重叠修改由 mine 胜出；
  当前 HTML 常将整张表的单元格输出在同一行。
- `lib/editor/table-ops.ts`：表头行与合并格限制源于现有存储和操作算法。
  格式扩容不意味着这些算法自动支持复杂表格。

## 2. 目标和范围

首要目标是让飞书粘贴形成的文档表格，在编辑、保存重开、只读、打印和引用
派生中具有同一语义。用户不需要为保存成功补表头或改写源码。

本轮设计覆盖：无表头表格、行列表头、列宽、合并范围、多个段落、列表、
代码、行内格式、图片和实体引用。覆盖意味着制定表达与降级规则，不意味着
一次开放全部创建与拖动操作。

电子表格公式、数据库字段、筛选排序不进入本契约。粘贴电子表格区域时，
只讨论剪贴板实际提供的静态内容，不承诺恢复公式或关联源。

不根据“单行且都是图片”自动改成分栏；不补造表头；不静默展开合并格。
若以后提供表格转分栏，应当是作者主动执行的转换。

## 3. 先确定语义模型

以下是概念模型，不是数据库表、最终 TypeScript 接口或新源码语法。

| 对象 | 必须表达的信息 |
| --- | --- |
| 表格 | 有序行列、列宽意图、布局约束 |
| 单元格 | 起始坐标、跨行数、跨列数、表头角色、有序内容块 |
| 内容块 | 段落、列表、代码、图片等块类型与其内部结构 |
| 行内内容 | 文本、格式、普通链接、实体引用、硬换行 |
| 图片/引用 | 实体身份、展示模式和有语义的参数；图片另存 alt |

建议不变量：

1. 单元格占据的逻辑网格不能重叠或越界；覆盖格不是额外空单元格。
2. 表头角色与第一行位置不能混为一谈，允许没有表头。
3. 空格、空段落、单元格缺失、被合并覆盖是四种不同情况。
4. 图片和引用不以 `textContent` 判空，保留所在格及块序。
5. 代码中的 URI、标签、分隔符是文字，不产生引用边或布局。
6. 素材展示 URL、chip 当前显示名不是持久身份；按既有解析和权限路径派生。
7. 空段落先保留。原始粘贴证据不足时，不能假定它们全部是编辑器噪声。

## 4. 文本表示候选与语言边界

### 4.1 修订方向：容器承载结构，单元格复用现有方言

保留已有 GFM。复杂表格的存储候选缩小为“Markdown 容器”和“显式开启 Markdown
内容的 HTML 结构壳”，比较见 §9。HTML 粘贴输入不决定正文必须存成 HTML。

初稿建议表格内全部改用 HTML，会要求图片、引用、提示框、分栏等维护第二套
持久化表达，并扩大 AI 校验和复制的分歧，因此撤回。HTML 仍然是外部粘贴、
历史兼容和复制导出的重要格式，但不能据此直接成为另一套正文语言。

只有证明完整语义可以往返时才能输出 GFM，不能沿用“首行是 th 即可”的判据。
宽度、多块、跨格、表头角色、块级图片与行内图片差别、对齐都参与判断。
简单表格的源码兼容、复杂表格何时切换表示，必须确定稳定且幂等的选择规则。
读时不自动保存规范化结果。

这里没有批准新增 `:::table`，也没有批准对整个文档开启任意 HTML 渲染。

### 4.2 内容语言保持一致，输入来源必须区分

建议：新存储表达中，每格是现有 Markdown 方言的块级内容容器。图片继续写
`![说明](/__cm__/asset/<id>)`，引用继续写 `[#](/__cm__/<kind>/<id>)`，
callout、列表、代码、颜色与空段落继续沿用已有语义；不为表格再定义 HTML 版本。
内容从正文移入单元格再移出时，语义不变。允许哪些块是结构能力问题，不能
通过换一种文本语言隐式限制它们。

飞书或历史普通 HTML 则仍按 HTML 解析：`<td>**甲**</td>` 中的星号是字面，
`<strong>甲</strong>` 才是加粗。输入转换应从语义树序列化出相应 Markdown，
不能把 HTML 的 textContent 当 Markdown 再解析一次，否则会凭空加格式。

若选择 HTML 结构壳，必须显式区分“Markdown 单元格”和历史 HTML 单元格；
属性名称、继承范围、关闭边界均需定稿。`markdown="block"` 只是已有方案的
参考，不是仓库当前支持的语法。关闭标签出现在代码内、实体转义、空行、
列表缩进都要由词法/语法层处理，不能用 DOM innerHTML 再解析代替。

若选择 Markdown 容器，结构边界不得与格内 `:::cols`、代码围栏、水平线
混淆；不能在全文字符串上找第一个关闭标记。两条路线均需在编辑与阅读侧
共享边界契约，再把单元格内容送入原有方言解析流程。

### 4.3 HTML 输入适配与不支持的内容

建议支持表格骨架 `table / thead / tbody / tfoot / tr / th / td`，并为
`colgroup / col` 定义宽度导入规则。单元格内容按现有文档节点逐项映射，
包括段落、换行、列表、代码、图片、普通链接、引用和已有行内格式。

嵌套表格、分栏、callout、任务项与其他块不能因为节点 schema 接受就自动
宣布支持；每类必须完成与现有序列化和渲染的组合验证后登记。

不能解释的结构需要保留可恢复的源内容并报告未支持项，不得无提示丢弃。
“原样保留未知内容”不等于执行它：未知标签、属性不直接传入渲染 DOM。
无法保证往返时，应局部保留为不可编辑源块；该机制尚未实现，若不引入，
必须沿用整篇源码保护，不能假定普通 TipTap 节点会替我们保留未知数据。

### 4.4 引用、素材必须有唯一语义入口

历史输入接受现存 `data-cm-src` 恢复素材身份；展示 `src` 不作为另一份真相。
若身份属性与展示 URL 矛盾，渲染应由身份重新解析，不能采信 URL 绕过解析。
新存储中的格内图片、chip 沿用现有 Markdown 表达。历史 HTML 与剪贴板中的
对应属性是输入适配，不再升级成第二种推荐写法。若最终设计仍需改变规约，
需同批更新规约、DEV_GUIDE、适用护栏和 AI 方言说明，并说明理由。

提取引用应遍历已解析的语义节点，复用相同身份解码器，避免为每种文本形式
另添全篇扫描正则。读取 HTML 表格中的身份也不能放宽 `canPublishAsset`
等既有挂载资格检查。历史漏边如何恢复需单独设计，不能在渲染请求里补写。

### 4.5 宽度与序列化

宽度需要区分“作者指定”和“浏览器测量结果”。建议列宽意图作为权威信息，
总宽及渲染 CSS 由它派生；像素、比例、自动宽度的最终取舍尚未确定。

历史样本同时有 table style、col style、cell colwidth，必须先定义冲突优先级。
不能随意选一个或将像素自动改成比例。缺少某列宽度也不等于该列宽度为 0。
窄屏应保留阅读能力，具体采用滚动或压缩需原型验证。

canonical 输出应固定属性顺序、实体转义和结构换行，并避免展示态 class、URL、
默认属性的重复持久化。预期“一格一段源码”有利于局部 diff，但还不能把它
当成协作方案：多行单元格、删列、合并格仍会产生结构冲突。

## 5. 保真与协作验收

设 P 为解析、S 为序列化、N 为明确声明的语义规范化：

- `P(S(model)) = N(model)`：包含坐标、表头、跨格、块序、格式、宽度和身份。
- `S(P(S(model))) = S(model)`：第二次往返不再改写。
- 引用提取结果应与语义树中真正的引用/嵌入一致，码内示例不计入。
- 编辑和阅读使用同一语义投影；不能以“HTML 字面还在”代替内容可用。
- 空白是否可折叠按上下文判断，代码、空段落和硬换行不能统一折叠。

结构保真不能只对同一有损解析器的输出自比。使用手工给定的预期网格、引用
集合和块序作为独立证据，并验证交换两格、删图片、改跨度等反例确实失败。

现有行合并不可直接视为支持富表格。至少验证：不同格同时编辑、同格同时
编辑、删行与改格并发、列宽修改与增列并发、合并格与格内修改并发。输出
若无法证明结构有效，应保留双方完整表格供冲突处理；具体交互待定。
不得简单对合并结果调用修表命令后保存，因为修复可能掩盖内容损失。

## 6. 脱敏样本与已完成实验

运行环境为仓库当前依赖：TipTap 3.30.3、tiptap-markdown 0.9.0、jsdom。
使用真实 Editor 和相关扩展做解析 → 序列化 → 重建；不连接数据库。
这些是现状实验，不是新格式实现的通过证明，也不是浏览器粘贴端到端验证。

| 样本 | 当前输出 | 已观察结果 | 新契约验收重点 |
| --- | --- | --- | --- |
| 无表头、图片独占一格 | HTML | 树和文本往返稳定；素材提取 0 | 图的位置、身份、alt 与派生边 |
| 空段落后接图片 | HTML | 树和文本往返稳定；素材提取 0 | 不自动丢空段落 |
| colspan=2，下一行两个普通格 | HTML | 树和文本往返稳定 | 网格覆盖关系、内容归属 |
| 一格内两项无序列表 | HTML | 树和文本往返稳定 | 列表结构与块顺序 |
| 星号、竖线、:::cols、&、转义标签 | HTML | 树和文本往返稳定 | 不递归解释 Markdown |
| 代码内含关闭标签、反引号、竖线 | HTML | 树和文本往返稳定 | 代码边界、不产生假表格 |
| 表头 + colwidth=200 | GFM | 文本稳定，重开后列宽丢失 | GFM 可表达性判断 |

图片脱敏输入示例：

```html
<table><tr><td><p></p><img src="/__cm__/asset/ast_sample_a" alt="参考图"></td></tr></table>
```

还试跑了未配置应用 `renderHTML` 的最小 mention 扩展，发现其 HTML 输出
不能稳定往返。但生产的 SmartTextarea 另有 renderHTML 配置，所以该实验
不作为线上缺陷证据。正式引用样本必须按完整应用配置验证所有 attrs 与身份，
不能使用这个最小装配代替。

后续需要补齐的样本：rowspan、首列表头、对齐、空表/空行、不规则行、
重叠/越界跨度、中文格式组合、带 query 参数的引用、@提及、两张相邻表、
表格前后空行、表格在列表/引用/分栏内、未知块、超长单元格，以及协作反例。
飞书原始样本必须分别采集普通文档表格与电子表格区域；Safari 仅提供
text/plain + text/html 的路径为必测，自定义 MIME 只能补充。

## 7. 实施前的决策与交付门槛

需要通过原型比较后定下来的事项：

1. Markdown 容器与 HTML 结构壳内显式 Markdown 的完整样本对照。
2. GFM 与复杂表格的选择规则，以及既有源码兼容；不得反复切换产生 diff。
3. 宽度模型、历史属性冲突规则、窄屏行为。
4. 未支持节点的保留机制，以及哪种输入需要阻止自动保存。
5. 结构冲突处理与历史漏边恢复，恢复动作沿用授权边界。

建议后续批次：

- 先建立脱敏 fixture 与语义预期，做独立解析/序列化原型，不写生产数据。
- 契约定稿后，同批实现编辑、阅读/打印、引用预收集与派生、保真和 AI 说明。
  手册、changelog、规则变更按仓库要求随实际行为变更提交。
- 验证存量读取和回滚路径，再决定迁移或保存时规范化；历史修订保持可读。

不得用“打开 HTML 阅读”“补一个提取正则”“让表头隐藏”作为完整交付。
是否需要数据库 migration 取决于最终存储和修复策略，本草案不预先承诺。

## 9. 二次调研：组合语言、复制与 AI（2026-09-26）

### 9.1 为什么撤回纯 HTML 内容方案

纯 HTML 内容并非技术上不可实现；问题是本仓库已经把正文、AI、引用派生和
源码编辑建立在同一套 Markdown 方言上。表格内切换内容语言会让每次添加
一种方言都同时修改两套持久化规则。复用 DOM renderHTML 也无法解决，
因为 DOM 含显示缓存、样式 class、素材展示 URL，目标与存储不同。

本次用脱敏 chip HTML 调用 `restoreAndCheckBody`：`span[data-content-mention]`
被判为不合法样式，闭合 span 另触发嵌套错误。校验器只把 span 视为颜色语法。
这是具体的接口分歧；它不证明每种实际 AI 操作均会失败，但证明“教 AI 写
表格 HTML 即可”与当前校验不兼容。

### 9.2 成熟方案提供了什么

| 路线 | 方言复用 | 主要成本 | 当前评价 |
| --- | --- | --- | --- |
| 全部 HTML 内容 | 要维护第二套内容表达 | 引用、布局、AI、转义均分叉 | 撤回作为优先存储方案 |
| HTML 结构壳 + 显式 Markdown 内容 | 可以复用 | 混合语言边界、旧 HTML 区分、代码内关闭标签 | 保留为原型候选 |
| Markdown 块容器 + Markdown 内容 | 可以复用 | 容器语法、嵌套界定、两侧解析器接入 | 优先做组合性原型 |
| ASCII grid table | 可以复用块内容 | 源码依赖列对齐，长 URI/中文/改格会扰动排版 | 不优先用于本库 |
| JSON/转义字符串封装每格 Markdown | 可以复用 | 多层转义、人工修改和 AI diff 成本 | 不作为默认正文格式 |

依据与限制：

- [Python-Markdown md-in-html](https://python-markdown.github.io/extensions/md_in_html/)
  有显式 markdown 属性，并区分 block/span；td 默认仅 span，完整块需明确选择。
  它还定义了逐层开启与父级限制。说明该路线可行，但不存在通用的“加一个属性
  就获得所有 Markdown”语义；仓库也没有安装这一 Python 实现。
- [Pandoc raw HTML](https://pandoc.org/demo/example33/8.14-raw-html.html)
  提供 HTML 块中解析 Markdown 的扩展。它的行为不是当前 markdown-it/remark
  的默认行为，也不自动包含本站方言。
- [micromark directive](https://github.com/micromark/micromark-extension-directive)
  提供容器与嵌套围栏规则；外层更多冒号可容纳内层容器。它不是表格标准，
  行列跨度等业务语义仍需定义。其未闭合容器延续到父级末尾的行为不能未经
  评估直接用于自动保存。现有 `:::cols 46,54` 也不符合它的属性写法，不能
  直接安装并把旧内容交给插件。
- [Pandoc grid tables](https://pandoc.org/demo/example33/8.9-tables.html)
  支持块内容与跨格，但需要源码列对齐。对长素材 URI 和中文的维护成本是
  本项目判断，并非已经做过 AI 成功率对比实验。

当前“容器优先”指优先验证其边界，不是已批准新的 `:::table` 文法。
两种候选都必须证明现有方言不需换写法；不能只用加粗和列表示例宣称成功。

### 9.3 不能用空行拼接冒充容器解析

本次在仓库 markdown-it 与 remark-parse 上实测：

| 输入 | markdown-it | remark |
| --- | --- | --- |
| `<table><tr><td>**甲**</td></tr></table>` | HTML，星号是文字 | 一个 html 节点 |
| td 后空行、加粗段落、空行、闭合标签 | 输出的 HTML 中有 strong | html + paragraph + html |
| td 添加 markdown="block"，不加空行 | 属性不启动 Markdown | 仍为 html 节点 |

空行使中间段落被解析，不等于解析器建立了 table → row → cell → paragraph
的树。后续方言、引用收集、代码隔离、范围编辑仍缺少单元格边界。该现象与
[CommonMark HTML 块规则](https://spec.commonmark.org/0.31.2/#html-blocks) 一致。

HTML+Markdown 候选必须在原始源码上识别受控结构与内容区，再分派内容解析；
不能先让浏览器修复完整 DOM，再从 innerHTML/textContent 取回 Markdown。
后者可能已经改掉实体、标签、文本位置，无法作为无损输入。

### 9.4 复用方言还需要复用正确的解析作用域

当前 `promoteColumnFences` 只扫描传入根节点的直接孩子；只读侧
`transformColumns` 也只处理传入节点的 children。本次对带分栏标记的单元格
DOM 调用整篇入口，识别出 0 组；直接对该 td 调用同一函数，识别出 1 组。

因此“每格放 Markdown”不是零改动，但需要的是提供单元格内容作用域、复用
原有规则，而不是重新定义分栏的 HTML 源码。原型需要验证表格在分栏内与
分栏在单元格内的作用域，以及原有不允许分栏嵌套的规则如何保持。

建议解析流程：先建立表格边界 → 每格作为独立块内容作用域解析 → 挂回语义树。
引用定义、脚注等依赖上下文的 Markdown 构造也要明确作用域，不能仅对每格
调用无上下文 parser 就宣称完成。现有不支持能力仍遵守原有保护规则。

### 9.5 复制输入、正文存储、复制输出分别约定

```text
飞书 HTML / 本站剪贴板 HTML / 历史 HTML
    → 各来源适配 → 文档语义节点
                         ↕
             正文格式（格内同一 Markdown 方言）
                         ↓
              AI 读取、修改与写入校验

文档语义节点 → 剪贴板 text/html（标准表格及已渲染内容）
文档语义节点 → 剪贴板 text/plain（选区对应的正文表示）
```

本站已有这两个剪贴板出口：ProseMirror 从 schema/clipboardSerializer 输出
HTML，tiptap-markdown 的 `transformCopiedText: true` 单独控制纯文本输出。
本次调用真实 `view.serializeForClipboard`，无表头图片表的 text/plain 是
当前 HTML 回退源码，text/html 是带 data-pm-slice 的表格 DOM。
证明两个出口可分别设计；不代表本站与飞书之间已经做过浏览器互贴验证。

建议契约：

- 飞书输入：解析提供的 HTML 语义，归一化成本站节点，再生成正文格式；
  不把源码中的普通星号误认成 Markdown。鉴权图片仍遵守既有上传/占位边界。
- 本站互贴：text/html 带可恢复的实体身份，结构进入相同节点模型；普通
  展示名不能代替身份。没有自定义 MIME 仍须成立。
- 复制到飞书：text/html 输出标准表格和可展示内容，不能包含需要飞书理解
  的私有容器源码。站内素材是否能被飞书取得、引用如何降级为可读信息需
  实测，不承诺复制后依然有站内实体语义或能绕过素材访问权限。
- 纯文本出口：整表与矩形选区输出相应表格表示，格内文本选区输出内容本身；
  复制源码单独保持源码语义。与电子表格的 TSV 需求作为另一种导出行为评估，
  不让它取代能表达多块内容的正文。
- 纯文本入口：当前仅开启 transformCopiedText，未开启 transformPastedText。
  不能假定复制源码后普通粘贴会自动恢复结构。需区分普通粘贴、粘贴纯文本
  与导入/粘贴 Markdown，决定产品行为后验证，而不是全局猜测每段文本。

验证选区必须覆盖整表、矩形多格、合并格边界、格内多段、从格内复制到正文、
正文复制进格内。不能只检查整篇 getMarkdown。Safari 的 text/html 和
text/plain 为基线；真实跨应用测试仍待执行。

### 9.6 AI 只增加结构知识，不增加第二套内容语言

建议 AI 继续读取和写入正文格式，单元格里的引用、图片、callout、颜色仍按
原方言书写。新增说明只涵盖行列、跨度、宽度、容器边界和禁止操作。
“AI 熟悉 HTML”不能作为成功率证据；目前没有对候选格式做模型实测。

读写链路仍需适配：`wiki_read` 的显示链接转换、提议写回的标题反解、
方言校验、引用提取必须理解单元格作用域和代码边界。格内沿用 Markdown
可减少变更，但不能保证现有全篇正则对嵌套代码和容器自动正确。

后续 AI 样本任务：只改一格文字；插入带引用的新行；从正文搬入提示框；
调整一个跨度；原样保留代码中的关闭标记；读取并修改飞书导入的图片表。
每项检查非目标格、实体身份、正文其余结构是否不变，并区分模型语法错误、
解析器错误和序列化丢失。比较 token/源码体积、成功率与错误可恢复性，
不以某个示例看起来简短作为最终选型依据。

### 9.7 修订后的优先级

先验证 Markdown 容器与显式 Markdown 单元格两条路线的组合性和复制出口，
再决定语法。现有 HTML 表格保留输入兼容职责；最终是否也作为新的 canonical
结构壳，取决于原型证据。内容方言不复制一套，是本轮修订的核心约束。


## 10. 本轮实现与源码可读性

### 10.1 存储文法

简单表格继续使用 GFM。没有表头、含跨度、显式列宽、对齐或多块内容的表格使用：

```markdown
:::table

:::row

:::cell colwidth=240

![参考图](/__cm__/asset/example)

说明文字

:::endcell

:::cell

- 第一项
- 第二项

:::endcell

:::endrow

:::endtable
```

边界各占独立段落，空行分隔；行、格采用具名闭合，与分栏的 `:::` 互不争用。
只有 `cell` 接受参数，顺序固定为 `header`、`colspan`、`rowspan`、`colwidth`、`align`。
缺省非表头、跨度 1、自动宽度、无对齐声明，写出时省略缺省值。
`colwidth` 的整数个数等于 colspan，0 表示自动宽度；align 仅 left/center/right。
参数重复、未知参数、网格缺口、越界跨度与冲突列宽不转换为表格。

格内复用现有 Markdown parser / serializer。分栏、提示框、图片、引用、样式、代码
不另造 HTML 版本；允许嵌套表格，解析深度设上限。边界先经 Markdown AST 判断，
代码围栏与行内代码不被切开，字面边界段落写为 `\:::endcell`。

### 10.2 可视化编辑之后的可读性

可读源码是持久格式的要求：稳定换行、固定参数顺序、不输出运行期 DOM、
不按最长单元格做 ASCII 对齐。复杂格的内容与普通正文写法相同。

编辑器记录上次源码和对应文档树，以顶层块的 canonical 结果判断修改范围。
未改块尽量保留原始字符（包括历史 HTML）；改动块写出 canonical。只打开文档
不自动回写。重复解析、保存的 canonical 结果必须稳定。

这不是完整的无损 CST 编辑器：源码块与编辑器节点无法一一对应（如引用式链接
定义、某些多段布局方言）时退回全文 canonical；本轮不承诺保留这些文档每个空格。
表格内以整表 canonical 保证稳定，尚不逐格保留作者的排版偏好。

### 10.3 输入、复制与保真

历史完整 HTML 表格通过标准 HTML parser 转换；保留表头、跨度、列宽、空段落、
素材身份。展示 src 让位于 data-cm-src。不能保留的节点、样式、非派生表宽或不完整
标签保持原文，交给现有保真保护，避免把浏览器自动修表当作无损转换。
没有批量迁移，没有读取即写回，也没有在线修复引用边。

复制的 HTML 继续来自 ProseMirror DOM serializer，普通软件得到标准 table；
纯文本复制得到 Markdown 容器。引用提取、AI 校验按 Markdown AST 排除代码示例。
AI 读取可识别的历史表格时得到同一容器格式，写入走现有权限和提案流程。
未来保存正文时，图片挂载边仍按已有素材发布资格检查派生。

保真检测新增单元格顺序、跨度、表头、列宽、对齐与格内块结构，不能再靠
全文相同词汇掩盖交换两格。提示框允许等价的 marker 换行变体。

### 10.4 协作与操作范围

富表格作为三路合并的结构单元；网格不变、不同格各自修改时合并格内容。
同格或结构冲突保留两份完整表格，并在正文提示作者核对，不拼接半个边界。
普通正文仍沿用既有行冲突策略。没有新增列宽拖动、合并菜单或重做已有拖动算法。

实现验证集中在 `tests/wiki/wiki-rich-table.test.tsx`、`wiki-table-merge.test.ts`，
同时保留原子节点表格测试与现有文档回归。
